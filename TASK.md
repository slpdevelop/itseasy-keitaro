# TASK.md --- Adrobot / Keitaro Campaign Manager

## 1. Цель проекта

Разработать приложение для автоматизации работы с рекламным трекером
**Keitaro** через его API.

Приложение должно закрывать два пользовательских сценария:

1.  Создание новой кампании с заранее заданной структурой и настройками.
2.  Редактирование существующей кампании: добавление и удаление офферов
    с корректным обновлением связанных числовых параметров.

Главный критерий качества --- не только наличие интерфейса, но и
корректное выполнение операций через API Keitaro. Все отображаемые
значения и результаты операций должны соответствовать фактическому
состоянию кампании.

## 2. Контекст предметной области

Keitaro --- рекламный трекер. В рамках задания он используется для
создания ссылок и маршрутизации входящего трафика по настроенным
правилам, а также для сбора статистики переходов.

Ключевые сущности, упомянутые в задании:

-   Кампания (Campaign).
-   Поток (Flow).
-   Оффер (Offer).
-   Домен (Domain).
-   Группа (Group).
-   Источник (Traffic source).
-   География пользователя (Geo / country code).

Названия сущностей в коде и API следует сверять с фактической
документацией и ответами используемой версии Keitaro API. Не
предполагать структуру API по названиям из этого документа.

## 3. Объём работ

### Часть A. Создание кампании

Реализовать интерфейс и серверную логику создания кампании.

#### Входные данные

Пользователь должен иметь возможность указать:

-   Название кампании.
-   Гео-код страны.
-   ID оффера Keitaro.

Кроме этих полей, создаваемая кампания должна быть связана с
настроенными доменом, группой и источником. Способ выбора этих сущностей
(фиксированная конфигурация, значения по умолчанию или выбор
пользователем) необходимо определить после изучения существующего
проекта и доступных API-методов. Не добавлять не предусмотренные
заданием обязательные поля без необходимости.

#### Требуемый результат

После успешного создания в Keitaro должна существовать кампания со
следующей конфигурацией:

-   У кампании задано введённое пользователем название.
-   Кампания содержит **два потока**.
-   Первый поток обрабатывает пользователей из указанной страны и
    перенаправляет их на Google.
-   Второй поток перенаправляет пользователей на выбранный оффер.
-   У кампании настроены домен, группа и источник.

Логика потоков должна быть реализована средствами Keitaro API, а не
имитироваться только на стороне интерфейса.

#### Основной пользовательский сценарий

1.  Пользователь открывает форму создания кампании.
2.  Вводит название кампании.
3.  Указывает гео-код страны.
4.  Указывает ID оффера Keitaro.
5.  Запускает создание.
6.  Приложение валидирует входные данные.
7.  Приложение создаёт кампанию и необходимые связанные
    сущности/настройки через API.
8.  Приложение сообщает об успехе и, если API возвращает идентификатор
    или ссылку кампании, показывает их пользователю.

#### Ошибочные сценарии

Необходимо корректно обработать как минимум:

-   Пустое или некорректное название.
-   Некорректный формат гео-кода.
-   Пустой или невалидный ID оффера.
-   Оффер, домен, группа или источник не найдены (если API позволяет
    проверить их отдельно).
-   Ошибку авторизации или недостаточные права API.
-   Сетевую ошибку, тайм-аут и ошибку API.
-   Частичное создание, когда часть последовательных API-операций прошла
    успешно, а следующая завершилась ошибкой.

Для частичного создания определить безопасную стратегию: откат уже
созданных сущностей, если он поддерживается и безопасен, либо понятное
сообщение о частичном результате с идентификаторами созданных объектов.
Не скрывать частичный успех и не сообщать об успешном создании всей
кампании, если операция завершилась не полностью.

### Часть B. Редактирование существующей кампании

Реализовать интерфейс для управления офферами в уже существующей
кампании.

#### Требуемые операции

-   Выбрать или открыть существующую кампанию.
-   Просмотреть текущие офферы кампании.
-   Добавить оффер в кампанию.
-   Удалить оффер из кампании.
-   После изменения отображать актуальные данные и корректные числовые
    значения.

Интерфейс можно спроектировать самостоятельно. Визуальное совпадение с
внутренним редактором из видео не является обязательным. Обязательны
работающие кнопки и корректные значения.

#### Важное требование к бизнес-логике

Подробная логика существующего редактора демонстрируется в видео:

https://youtu.be/jNloscEWCjA

**Перед реализацией редактора необходимо изучить видео и зафиксировать
его поведение.** В частности, определить:

-   Какие именно числовые значения показываются рядом с офферами.
-   Как эти значения меняются при добавлении оффера.
-   Как они пересчитываются при удалении оффера.
-   Есть ли ограничения на количество офферов.
-   Как распределяются веса/проценты/доли трафика, если такие параметры
    присутствуют.
-   Что происходит при удалении последнего оффера.
-   Какие действия сохраняются автоматически, а какие требуют отдельного
    подтверждения.

Не считать перечисленные параметры подтверждёнными особенностями
системы: это список вопросов для изучения видео и проверки фактического
API. Не придумывать алгоритм пересчёта до получения достаточных данных.

#### Основной пользовательский сценарий

1.  Пользователь открывает раздел редактирования кампаний.
2.  Выбирает существующую кампанию.
3.  Приложение загружает и отображает её актуальные офферы и связанные
    значения.
4.  Пользователь добавляет или удаляет оффер.
5.  Приложение проверяет допустимость операции.
6.  Изменение отправляется в Keitaro API.
7.  После успешного ответа приложение получает или повторно загружает
    актуальное состояние кампании.
8.  Интерфейс показывает обновлённый список и корректные числовые
    значения.

#### Ошибочные сценарии

Необходимо обработать:

-   Кампания не найдена.
-   Оффер не найден.
-   Попытка добавить уже присутствующий оффер, если дубли запрещены.
-   Попытка удалить отсутствующий оффер.
-   Недопустимое состояние кампании после удаления.
-   Ошибки API, авторизации, сети и тайм-ауты.
-   Неуспешное сохранение изменений.

При ошибке интерфейс не должен показывать неподтверждённое состояние как
сохранённое. Предусмотреть обновление данных с сервера после неудачной
операции или явное отображение того, что локальное состояние не
синхронизировано.

## 4. Интеграция с Keitaro API

До реализации необходимо:

1.  Найти и изучить документацию API для используемой версии Keitaro.
2.  Определить методы для получения справочников (офферы, домены,
    группы, источники).
3.  Определить методы создания кампании и её потоков.
4.  Определить методы получения и изменения существующей кампании и её
    офферов.
5.  Проверить реальные форматы запросов и ответов.
6.  Проверить обязательные поля и допустимые значения.
7.  Уточнить, какие операции выполняются отдельными запросами и в каком
    порядке.

Требования к интеграционному слою:

-   Вынести HTTP-взаимодействие с Keitaro в отдельный клиент/сервис.
-   Не размещать прямые API-запросы в обработчиках интерфейса.
-   Централизовать базовый URL, авторизацию, тайм-ауты и обработку
    ошибок.
-   Не дублировать формирование URL, заголовков и обработку ответов.
-   Использовать явные DTO/схемы или другой принятый в проекте способ
    валидации данных.
-   Разделять ошибки валидации, ошибки API и сетевые ошибки.
-   Не логировать API-токены и другие секреты.
-   Не выполнять повторно потенциально неидемпотентную операцию
    автоматически без понимания последствий.

Точный API-контракт должен быть подтверждён документацией или реальными
тестовыми ответами. Не выдумывать endpoint, HTTP-метод, поля JSON или
алгоритмы.

## 5. Конфигурация и безопасность

-   API-токен и адрес Keitaro должны храниться в конфигурации окружения
    или в существующем механизме секретов проекта.
-   Секреты не должны попадать в Git, клиентский bundle, ответы API
    приложения или логи.
-   Добавить пример конфигурации без реальных секретов (например,
    `.env.example`), если это соответствует структуре проекта.
-   Проверять наличие обязательных настроек при запуске или перед
    обращением к API.
-   Не передавать API-токен на frontend.
-   Не добавлять реальные учетные данные в тесты и документацию.

## 6. Интерфейс и UX

Общие требования:

-   Интерфейс должен быть понятным и функциональным.
-   Пользователь должен видеть состояние загрузки во время запросов.
-   Кнопки операций должны блокироваться или защищаться от повторного
    нажатия, пока запрос выполняется.
-   Ошибки должны отображаться понятным сообщением.
-   Успешное действие должно сопровождаться явным подтверждением.
-   Для опасных действий (например, удаления оффера) предусмотреть
    подтверждение, если это соответствует UX проекта.
-   После успешного изменения показывать данные, подтверждённые
    сервером.
-   Не показывать фиктивные данные вместо результатов API, кроме явно
    обозначенного demo/mock-режима для разработки.

Пример интерфейса создания кампании находится в исходном задании. Его
следует использовать как ориентир, а не как требование к точному
копированию.

## 7. Технические ограничения и принципы реализации

Стек и архитектура должны определяться существующим репозиторием и
дополнительными требованиями заказчика. Если репозиторий уже содержит
приложение, необходимо продолжать его текущую архитектуру и не заменять
стек без веской причины.

До начала разработки:

-   Изучить структуру репозитория и существующие соглашения.
-   Найти текущие точки входа, конфигурацию, зависимости и тесты.
-   Проверить, нет ли уже готового клиента Keitaro или моделей
    соответствующих сущностей.
-   Составить краткий план реализации и список неизвестных требований.

Не выполнять лишний рефакторинг, не относящийся к заданию.

## 8. Тестирование

Минимальный набор проверок:

### Создание кампании

-   Валидация обязательных полей.
-   Формирование корректных данных для API.
-   Создание кампании с двумя требуемыми потоками.
-   Корректная настройка страны и редиректа первого потока.
-   Корректная настройка редиректа второго потока на выбранный оффер.
-   Настройка домена, группы и источника.
-   Обработка API-ошибок и частичного создания.

### Редактор кампании

-   Загрузка кампании и её офферов.
-   Добавление оффера.
-   Удаление оффера.
-   Корректный пересчёт числовых параметров по правилам, подтверждённым
    видео/API.
-   Запрет недопустимых операций.
-   Синхронизация интерфейса с сервером после изменения.
-   Обработка неуспешного сохранения.

### Общие проверки

-   Секреты не попадают в клиентский код и логи.
-   Нет фиктивного сообщения об успехе при ошибке API.
-   Нет необработанных исключений в основных сценариях.
-   Существующие тесты и проверки проекта не сломаны.

Для unit-тестов API-клиент следует изолировать от реальной сети с
помощью моков. Интеграционные тесты с реальным Keitaro запускать только
при наличии отдельного тестового окружения и явной конфигурации.

## 9. Критерии приёмки

Задание можно считать выполненным, когда:

-   [ ] Пользователь может создать кампанию, указав название, гео-код
    страны и ID оффера.
-   [ ] В Keitaro создаётся кампания с двумя потоками.
-   [ ] Первый поток направляет пользователей из заданной страны на
    Google.
-   [ ] Второй поток направляет пользователей на выбранный оффер.
-   [ ] Кампания связана с корректными доменом, группой и источником.
-   [ ] Пользователь может открыть существующую кампанию.
-   [ ] Пользователь может добавить оффер.
-   [ ] Пользователь может удалить оффер.
-   [ ] Числовые значения редактора соответствуют логике исходного видео
    и фактическим данным API.
-   [ ] После операций интерфейс отражает подтверждённое сервером
    состояние.
-   [ ] Ошибки API и частичные операции обрабатываются корректно.
-   [ ] Секреты не хранятся в исходном коде и не раскрываются клиенту.
-   [ ] Основные сценарии покрыты тестами.
-   [ ] В README описаны запуск, настройка окружения и использование
    приложения.

## 10. Неизвестные требования и вопросы для уточнения

Эти пункты нельзя считать решёнными без изучения исходных материалов или
проекта:

1.  Какая версия Keitaro используется и где находится API.
2.  Какой домен, группа и источник должны назначаться по умолчанию.
3.  Должен ли пользователь выбирать домен, группу и источник в
    интерфейсе.
4.  Как именно задаются условия и порядок двух потоков.
5.  Какой именно URL Google должен использоваться для редиректа.
6.  Как в редакторе рассчитываются и отображаются числовые значения
    офферов.
7.  Допускаются ли повторяющиеся офферы.
8.  Какие ограничения существуют при удалении офферов.
9.  Какой формат запуска и сдачи ожидается (локально, Docker, деплой и
    т. п.).

Приоритет источников истины: фактическая документация и ответы Keitaro
API, исходное видео редактора, существующий код проекта, затем это
техническое описание. При обнаружении противоречий зафиксировать их до
реализации, а не выбирать поведение наугад.
