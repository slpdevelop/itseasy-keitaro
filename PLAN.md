# PLAN_B.md --- План реализации серверной части Adrobot

## 1. Цель и главный порядок работ

Серверная часть разрабатывается на **FastAPI + SQLAlchemy** для двух сценариев из
`TASK.md`:

1.  Создание кампании с двумя потоками: первый — пользователи
    указанной страны перенаправляются на Google; второй — на выбранный
    оффер. У кампании должны быть настроены домен, группа и источник.
2.  Редактирование существующей кампании: просмотр офферов, добавление и
    удаление, корректное обновление числовых значений по подтверждённым
    правилам.

**Критически важное требование:** реальная интеграция с Keitaro
выполняется строго на последнем этапе — после полной реализации и тестирования серверной части с помощью тестового имитатора внешнего сервиса. До финального этапа
запрещены реальные HTTP-запросы к Keitaro и реализация конкретных
маршрутов API Keitaro и тел запросов.

`TASK.md` — источник функциональных требований; `AGENTS.md` —
правила работы агента; `PLAN_B.md` — план реализации с разделами "Выполненные" и "Очередные задачи";
этот файл — порядок разработки серверной части.

## 2. Стек и зависимости

### Основные пакеты

    Пакет                   Назначение
    ----------------------- -----------------------------------------
    `fastapi`               HTTP API, внедрение зависимостей, описание API (OpenAPI)
    `uvicorn[standard]`     ASGI-сервер
    `pydantic`              объекты передачи данных (DTO) и валидация данных
    `pydantic-settings`     Конфигурация из переменных окружения
    `sqlalchemy[asyncio]`   Асинхронный ORM и работа с БД
    `asyncpg`               Асинхронный драйвер PostgreSQL
    `alembic`               Миграции БД

### Тестирование и качество кода

    Пакет              Назначение
    ------------------ ------------------------------------------------
    `pytest`           Запуск тестов
    `pytest-asyncio`   Тесты асинхронного кода
    `httpx`            Тестирование API приложения; позднее HTTP-клиент
    `respx`            Подмена HTTP-ответов при тестировании HTTPX на этапе интеграции
    `pytest-cov`       Покрытие тестами
    `ruff`             Проверка стиля кода и автоматическое форматирование
    `mypy`             Статическая проверка типов
    `pre-commit`       Опциональные локальные проверки перед коммитом

### Инфраструктура

-   PostgreSQL — основная БД.
-   Docker Compose — локальный запуск PostgreSQL и серверной части, если проект
    ещё не имеет принятого способа запуска.
-   `.env` — локальная конфигурация, не добавлять в Git.
-   `.env.example` — список переменных с примерными значениями.

Использовать актуальные совместимые версии и один менеджер зависимостей,
принятый в репозитории (если его нет — выбрать `uv` либо стандартный
`pip` с фиксацией версий и ограничений зависимостей). Не вводить параллельно несколько
менеджеров.

### Принципы по зависимостям и БД

-   Не добавлять Redis, Celery, JWT/OAuth, регистрацию пользователей и
    дополнительные DI-фрейворки без подтверждённого требования. В
    исходном задании этого нет.
-   `python-multipart` добавлять только при появлении реального
    multipart маршрута API.
-   Keitaro остаётся источником истины по кампаниям и офферам. Не
    создавать локальную копию этих сущностей и не выдавать кэш за
    актуальные данные.
-   SQLAlchemy/PostgreSQL использовать для действительно локальных
    данных приложения (например, аудит операций/технические метаданные),
    если это оправдано. Не создавать таблицы только ради использования
    ORM. Не хранить токен Keitaro в открытом виде в БД.
-   Если после анализа репозитория выяснится, что постоянные локальные
    данные не нужны, зафиксировать это решение и не изобретать лишнюю
    бизнес-модель.

## 3. Целевая архитектура

Примерная структура (адаптировать под существующий репозиторий, не
создавать пустые абстракции):

```text
backend/
├── app/
│   ├── main.py
│   ├── api/
│   │   ├── deps.py
│   │   └── v1/
│   │       ├── router.py
│   │       └── endpoints/
│   ├── core/
│   │   ├── config.py
│   │   ├── exceptions.py
│   │   └── logging.py
│   ├── db/
│   │   ├── base.py
│   │   └── session.py
│   ├── domain/
│   │   ├── campaigns/
│   │   └── offers/
│   ├── schemas/
│   ├── repositories/
│   ├── services/
│   └── adapters/
│       └── provider/
│           ├── ports.py
│           └── fake.py
├── tests/
│   ├── unit/
│   ├── integration/
│   └── api/
├── alembic.ini
├── pyproject.toml
├── .env.example
└── README.md
```

Разделение ответственности:

-   `api` — HTTP, коды ответов, зависимости, преобразование ошибок.
-   `schemas` — объекты передачи данных Pydantic для запросов и ответов.
-   `domain` — бизнес-правила, не зависящие от FastAPI, SQLAlchemy и
    Keitaro.
-   `services` — сценарии использования и координация сценариев.
-   `repositories` — локальная БД.
-   `adapters` — внешние провайдеры. Реальный адаптер Keitaro
    создаётся только на последнем этапе.
-   `core` — настройки, логирование, общие исключения.

Не смешивать SQLAlchemy ORM-модели с схемы передачи данных Pydantic. Не помещать
бизнес-логику в функции обработчика API.

## 5. Общие правила работы

-   Выполнять один небольшой подэтап за раз.
-   До изменений изучать только релевантные файлы.
-   После каждого подэтапа запускать узкие тесты и проверять diff.
-   Не переходить дальше при падающих проверках.
-   Обновлять `PLAN_B.md` после каждого этапа и перед завершением
    сессии.
-   Сохранять контекст для локальной квантованной модели: короткие
    задачи, компактные выводы и точный следующий шаг.
-   Не генерировать всю серверную часть одним большим запросом.
-   Не добавлять неоговорённые функции (авторизация, кэш, очереди фоновых задач,
    локальную копию Keitaro) без обоснования.
-   До этапа 12 допустимы только интерфейс провайдера, тестовый адаптер и тестовые наборы данных. Никаких реальных Keitaro HTTP-вызовов.
-   Не использовать учётные данные рабочего окружения и кампании рабочего окружения для
    тестов.
