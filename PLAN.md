# PLAN.md --- План реализации серверной части Adrobot

## 1. Цель и главный порядок работ

Серверная часть разрабатывается на **FastAPI + SQLAlchemy** для двух сценариев из
`TASK.md`:

1.  Создание кампании с двумя потоками: первый — пользователи
    указанной страны перенаправляются на Google; второй — на выбранный
    оффер. У кампании должны быть настроены домен, группа и источник.
2.  Редактирование существующей кампании: просмотр офферов, добавление и
    удаление, корректное обновление числовых значений по подтверждённым
    правилам.

**Критически важное требование:** реальная интеграция с Keitaro
выполняется строго на последнем этапе — после полной реализации и тестирования серверной части с помощью тестового имитатора внешнего сервиса. До финального этапа
запрещены реальные HTTP-запросы к Keitaro и реализация конкретных
маршрутов API Keitaro и тел запросов.

`TASK.md` — источник функциональных требований; `AGENTS.md` —
правила работы агента; `PLAN.md` — план реализации с разделами "Выполненные" и "Очередные задачи";
этот файл — порядок разработки серверной части.

## 2. Стек и зависимости

### Основные пакеты

| Пакет                   | Назначение                                     |
|-------------------------|-------------------------------------------------|
| `fastapi`               | HTTP API, внедрение зависимостей, OpenAPI       |
| `uvicorn[standard]`     | ASGI-сервер                                    |
| `pydantic`              | объекты передачи данных (DTO) и валидация       |
| `pydantic-settings`     | Конфигурация из переменных окружения            |
| `sqlalchemy[asyncio]`   | Асинхронный ORM и работа с БД                  |
| `asyncpg`               | Асинхронный драйвер PostgreSQL                 |
| `alembic`               | Миграции БД                                    |

### Тестирование и качество кода

| Пакет              | Назначение                                     |
|--------------------|-------------------------------------------------|
| `pytest`           | Запуск тестов                                 |
| `pytest-asyncio`   | Тесты асинхронного кода                       |
| `httpx`            | Тестирование API приложения                   |
| `respx`            | Подмена HTTP-ответов при тестировании         |
| `pytest-cov`       | Покрытие тестами                              |
| `ruff`             | Проверка стиля кода и форматирование          |
| `mypy`             | Статическая проверка типов                    |

### Инфраструктура

-   PostgreSQL — основная БД.
-   Docker Compose — локальный запуск PostgreSQL и серверной части.
-   `.env` — локальная конфигурация, не добавлять в Git.
-   `.env.example` — список переменных с примерными значениями.

Использовать актуальные совместимые версии и один менеджер зависимостей (pip/uv). Не вводить параллельно несколько менеджеров.

### Принципы по зависимостям и БД

-   Не добавлять Redis, Celery, JWT/OAuth, регистрацию пользователей без подтверждённого требования.
-   Keitaro остаётся источником истины по кампаниям и офферам.
-   SQLAlchemy/PostgreSQL использовать для действительно локальных данных приложения.
-   Если постоянные локальные данные не нужны — зафиксировать это решение.

## 3. Целевая архитектура

```text
backend/
├── app/
│   ├── main.py
│   ├── api/
│   │   └── v1/
│   │       ├── router.py
│   │       └── endpoints/
│   ├── core/
│   │   ├── config.py
│   │   └── exceptions.py
│   ├── tests/
│   │   ├── conftest.py
│   │   └── api/
```

Разделение ответственности:

-   `api` — HTTP, коды ответов, зависимости, преобразование ошибок.
-   `schemas` — объекты передачи данных Pydantic для запросов и ответов.
-   `domain` — бизнес-правили, не зависящие от FastAPI/SQLAlchemy.
-   `services` — сценарии использования и координация.
-   `adapters` — внешние провайдеры. Реальный адаптер Keitaro только на финальном этапе.
-   `core` — настройки, логирование, общие исключения.

## 5. Общие правила работы

-   Выполнять один небольшой подэтап за раз.
-   До изменений изучать только релевантные файлы.
-   После каждого подэтапа запускать узкие тесты и проверять diff.
-   Не переходить дальше при падающих проверках.
-   Обновлять `PLAN.md` после каждого этапа и перед завершением сессии.
-   Сохранять контекст для локальной квантованной модели: короткие задачи, компактные выводы.
-   Не генерировать всю серверную часть одним большим запросом.
-   **Важное правило:** Не создавать пустую структуру папок. Папки и файлы должны создаваться только под конкретные изменения или написания кода.
